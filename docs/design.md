# Downpad design

This document describes the main design of Downpad. It intentionally omits internal API listings, historical migration notes, and development plans.

## Technology

Downpad is an Electron desktop application:

- The frontend uses React and TypeScript.
- Milkdown Crepe provides the WYSIWYG Markdown editor.
- CodeMirror provides the Markdown source editor.
- The TypeScript main process handles native file access, settings, recovery data, printing, and desktop integration.
- Local application data is stored in human-readable or standard formats such as Markdown, TOML, and JSON.
- pnpm applies the fixes in `patches/` to dependencies on install. Each patch explains itself in a comment. The ProseMirror patch keeps a caret key such as End, pressed right after a click into the document view, from being undone on a busy machine. It also keeps a selected block selected when Chromium moves the selection to the start of the document. Chromium does that to a selection it cannot show whenever the page takes focus, after the focus events. On Linux that happens when the window is activated again after another app had focus or a native dialog such as Save As closes. It also happens while the page has focus already, before each input event that DevTools sends in the tests. A block between two blocks that take no caret, such as an image between two code blocks, is such a selection. ProseMirror's own check puts the selection back only if it reads the move within 200 ms of a focus event and as the first selection the document can hold. It missed the move in a document that starts with a block that takes no caret, such as a rule, on a page busy for longer and with no focus event, and the next key went to the start of the document. It also took a move by a key such as Ctrl+Home within 200 ms of focus for the browser's and undid it, so the patch skips that check after a key that can move the selection. The patch puts the selection back when no click, touch or key other than a modifier moved the selection since ProseMirror set it. An input that leaves the selection where it was, such as Ctrl+C, counts as no move once its event is over. A key checks for such a move before it goes in. The start of the document is where ProseMirror reads its first text, or a gap cursor before it when the document starts with a block that takes no caret, such as a horizontal rule. ProseMirror itself types a key over a selection that is not text, such as a selected block, selected table cells or a selection of the whole document, and left text that comes without a key to Chromium. Over a block between two paragraphs, such as an image, Chromium removed the DOM range around the block, which joined the paragraphs, and over two selected cells it replaced the text of only one. So the patch types such text over any selection that is not text as ProseMirror types a key. A move of the selection that ProseMirror has not read yet is read first, so text that comes right after Page Up goes where Page Up put the caret and leaves the block, while a move to the start of the document by the page goes back. A composition still goes to Chromium, since it cannot be cancelled. The document view readies such a selection for one first, as described below for End. ProseMirror 1.42.7 includes the fix for the `posAtDOM` regression in 1.42.6, so the patch no longer carries it. Version 1.42.6 read a position before a node view's content as the node's end, so a press on a list item's bullet, which Crepe draws before the item's text, put the caret after the item instead of at the start of its text. The Milkdown components patch keeps text typed right after Tab, Shift+Tab, Enter, undo or redo in a list where it was typed. Each of these redraws a list item, which puts back the caret it saw then once the next frame comes. On a busy machine that frame can come after keys typed meanwhile, and the caret jumped back into them, so a key, click or edit before the frame now cancels it.

Electron packages Chromium and Node.js with the app. This gives development and installed builds the same browser runtime at the cost of a larger installer.

## Editing model

Each open document has one canonical Markdown string. The document and source editors are two views of that same content:

- Document view renders and edits formatted Markdown.
- Markdown view exposes the source directly. It parses GitHub Flavored Markdown with a leading YAML frontmatter block, and colors it with VS Code's default Markdown and YAML token colors (Light+ and Dark+). It reads display math in `$$` fences outside lists and quotes as the document view does, with blank lines in the math and math that is not closed running to the end of the text, and leaves the math in the body color.
- Split view shows both and synchronizes changes between them.

If the document view cannot be built for a tab, because Milkdown's create fails (for example when the parser overflows its stack on deeply nested quotes), the tab records the error and shows its Markdown view alone, whatever the window's layout. The layout control shows Markdown while that tab is active, and the window's layout and the `defaultView` setting stay as they are. The notice bar under the tabs explains the fallback and offers Try again. Any other banner, such as a file changed on disk, takes the bar first. Try again, choosing Document or Split, or reloading the file builds the document view again from the tab's current text. A failed create still ends, because Downpad skips Milkdown's destroy for an editor that is still creating. That destroy would otherwise try again every 50 ms forever. The print workspace prints the Markdown version of a document it cannot render.

Building the document view can take a moment, for example while local images are looked up, and the Markdown view on screen stays editable meanwhile. If the text or a document setting changes during the build, Downpad builds the view again from the current text and settings before it shows it. So the document view never shows older text, and its edits always reach the tab. If the text changes during each of five builds in a row, Downpad stops and shows the tab's Markdown view with the notice, as for a failed create.

Reloading a file from disk, or opening a file in place of an empty Untitled tab, replaces the tab's text. While the document view is built for the new text, the Markdown view on screen still holds the old text, so Downpad ignores typing there until that view is built again too. That typing would otherwise write the old text back over the new. Each view is built again from the new text when it is next shown. Its undo history starts there, and the document view looks its images up again, so an image that has appeared on disk shows. Downpad drops a split mirror of an edit made before the new text arrived. That mirror would copy the new text into a view built before it and count that view as up to date, with its undo history and image answers from before.

Downpad changes the views one step at a time, such as a tab switch, a layout switch or a reload. A tab switch, an open, a reload or a layout choice that comes while another step still builds a view waits for that step, and Downpad then shows the active tab again, in the layout the layout control shows. So the window never keeps showing another tab's Markdown view, where typing would be ignored, and a view built from the text before a reload is built again from the new text. A layout or a tab chosen while a layout switch, Try again or a tab switch still runs is ignored, and the layout control and the tabs stay as they were. A layout switch or a tab switch that waits for another step counts as running until Downpad shows the active tab. So once a layout is chosen during a reload, another layout or a tab chosen before the document shows is ignored.

Opening a document never changes its text. The document view reports the exact source it was given until the user edits the body there. An edit there writes only the top-level blocks it changed in Milkdown's Markdown style. Every other block keeps its source text. Two blocks that were neighbours in the source keep the blank lines between them. A new join, next to a changed or removed block, keeps the source's line break when the text still reads as the same blocks, and otherwise gets a blank line. Link reference definitions, which the document view does not show, stay while a block that keeps its source text uses them. A definition that nothing in the source used stays as long as any block keeps its source text.

The document view pairs its blocks with the source's blocks. Blocks the user did not touch are the same ProseMirror nodes as when the source was parsed, and the rest pair by how Milkdown writes them. The positions of the source's blocks come from the parse that opened it. Every new join is checked before the text is used. Rules that follow from how the parser ends each kind of block settle most joins without reading anything back, for example a blank line after a paragraph or a closed fence. The other joins are read back with Crepe's parser, in a window that starts where the text above cannot change how it reads and ends with the first lines of the block below. The window must read as exactly its blocks. A block that keeps its source text must read as the same kind of node over the same text and open the same blocks on its first line, such as a quote with a list in it. A changed block must read as the document's block in Milkdown's form, or as that form reads on its own. Each block's text ends on its last line, and the line break after it stays with the blank lines below it. In a file with no line break at its end, a kept block that becomes the last one keeps the line break that followed it, because a tag alone on the last line of a list, quote or footnote reads as part of it only with a line break after it. Where a window reads otherwise, the join at fault gets a blank line and the window is read again. The document view writes the whole body in Milkdown's style when a window still reads otherwise (a new list right below a list, for example), when a changed block held a definition, when a new footnote could turn text in a kept block into a reference, when raw HTML in a changed block holds a line that could be a definition and a kept block has bracketed text it could turn into a link or footnote, when a definition the file keeps could turn bracketed text in a changed block into a link, when indented code could end in another place than in the source, as it can right below a list or quote, when text follows a block that read as it did only at the very end of the file, when the text below a list or footnote that ends in a fence, math block or HTML block the file left open, such as a comment with no `-->` or a `<pre>` with no `</pre>`, would change what that block holds, when the source's blocks do not map one for one onto the document's, or when reading the windows back would take longer than writing the whole body. The same document always gets the same text, whatever was written before it. A split mirror sync makes the synced text the new source and records that with the body in the undo history, so undoing a sync writes the body from before it with that body's own source.

The document view shows the YAML frontmatter in an editable table above the editor. The table writes back only the lines it changes. A press on the table outside its keys, values and buttons, such as on its caption or in the blank space around them, leaves focus where it was. Chromium moved focus to the page there, and the next key went nowhere. A press on a key or value, also a read-only one, stays with the browser, so its text can be selected. Each change to the block is a step in the editor's undo history, so undo and redo move through table and body edits in one order. A split mirror sync records the block and the blank lines after it with the body, so its undo restores all three.

Crepe's table view turns a click on a cell's text, or in the space right of it, into a selection of the cell's whole paragraph a frame later, unless the caret is already in that cell. The next keystroke then replaced the cell's text. Downpad replaces that view with a subclass that leaves a press inside the cells to ProseMirror, as in any paragraph, and to prosemirror-tables, which selects cells on a drag across them or out of the table. Crepe's row and column handles sit outside the cells and keep Crepe's handling.

Crepe's view also had ProseMirror draw a table again, with new cells, whenever only the selection or highlights in it changed. In the split, a click in the document pane right after a Markdown edit first brings that pane up to date, which ends a cell selection there. The click then landed on a cell that was gone, placed no caret, and left the focus in neither pane. The subclass updates a table whose content is unchanged in place, unless a whole row or column is selected in it. Crepe's new view opens the menu of a selected row or column, such as after a click on its handle, on the button that adds it, or a drag of it by its handle, so then the table is still drawn again. After every other update, whether the content changed or not, the subclass closes a row or column menu once the selection it acts on is gone. The redraw did that only when the content was unchanged, so a menu stayed open after a Markdown edit of a cell in the split. Crepe's menu buttons act on pointerdown, and the click that follows reaches the handle, which selects the row or column at its place. After a row's Delete that is the row that moved up, and Crepe's new view opens its menu, so Delete again removes that row too. The Delete itself ends the row selection, so during a press that started on a handle or in its menu the subclass closes a stale menu only once the press and its click are over. Closing it at once hid the button under the pointer before the release, so the click landed on the cell below and no row was selected.

The buttons that add a row or a column took focus on the press, as buttons do. Their click adds the row or column and selects it, and the table is drawn again for its menu without the button that had focus, so focus went to the page and the next key was lost. The subclass keeps focus where it was on a press on such a button and focuses the document after its click, so the next key goes to the new row or column, as after a click on a handle.

Crepe's view also kept every drag event in a table from ProseMirror, and cancelled dragover there but not dragenter. When the element under the pointer changes, Chromium sends only a dragenter, which happens on every update while the page scrolls under a still pointer. With that last update not cancelled, Chromium dropped a block dragged by its handle into the cell itself, as a copy of its text, and the block stayed where it was. With the last update a cancelled dragover, no one took the drop, so text from another app dropped on a cell did nothing. The subclass leaves the events of a drag that ProseMirror tracks in `view.dragging`, such as a block dragged by Crepe's block handle or selected text, and of a drag that carries text from elsewhere, such as another app or the Split view's Markdown pane, to ProseMirror, which cancels the dragenter and takes the drop. Crepe's block handle starts its drag on the handle itself, outside the editor, and only records it in `view.dragging`. The table keeps the drags of its own row and column handles, which carry no text, and drags of files, which the app takes, as before.

Crepe's drop indicator offers every block edge as a place to drop, including the edges between a table's rows and cells. A block put in there cut the table in two, or pulled a cell out into a new table. A drop whose nearest edge is inside a table therefore goes in above or below the whole table, at its edge nearer the pointer (`dropEdge.ts`). The indicator also had its own timing. It found its edge again only for a dragover at a new point, and otherwise kept the edge it found for that point. It hid its line 30 ms after a dragleave unless a dragover followed, and when the element under a still pointer changes, as it does while the page scrolls under it, Chromium sends a dragenter and a dragleave but no dragover. After such a scroll the indicator put the drop in at the edge that had been under the pointer before, which could be one between a table's rows, while its line stayed at its old place on the screen or hid. Downpad therefore removes the indicator's plugin and keeps only its state and the element that draws its line. A `handleDrop` prop of the editor view puts every drop in at the edge it finds from the page as it is at the drop, and a plugin of Downpad's draws the line at the edge the same code finds, on every dragenter and dragover over the document and on every scroll during the drag. The line hides once the drag leaves the document, which a dragleave whose related target is outside the editor, or missing as when the drag leaves the window, tells. It also hides at any drop or end of a drag in the window, in the capture phase on the document, so a file drop that the app takes before the editor hears it, or a drag cancelled with Escape, leaves no line and no work behind. Measuring every block takes long in a long document, since each `nodeDOM` lookup walks the blocks before it, so the code keeps the boxes of the blocks relative to the editor's box until the document or the editor's size changes, as the indicator kept its edges. A scroll moves the editor and its blocks together, so a drag that scrolls the page measures the page once. The line hides where a move would leave the dragged block or selection where it is, as the indicator did at its own edges. Crepe's block handle marks every drag it starts as a move, but ProseMirror decides at each drop, and copies while Ctrl, or Option on macOS, is held. The plugin therefore decides by ProseMirror's rule for the current event, so the line still shows for a copy right beside the dragged block, where the copy goes in. The page scrolls to show the drop when it lands out of view, as it can at the far edge of a tall table. A file dropped on a table goes in at the same edge (`fileDrop.ts`).

Crepe draws a fenced code block, math block or Mermaid diagram with a CodeMirror editor of its own, and its view keeps every event on the block from ProseMirror. CodeMirror took the drop of a block dragged by its handle, or of text selected in the document, onto the code. It put the text in at the pointer and, since it deletes only text dragged from within itself, left the original where it was, so the content was there twice. Over the block's toolbar or preview nothing cancelled the drag events, so nothing took the drop. For a drag that ProseMirror tracks in `view.dragging`, a listener on the editor in the capture phase now cancels each drag event on a code block before CodeMirror hears it (`dropEdge.ts`). CodeMirror ignores a cancelled event, and the cancelled dragenter and dragover allow the drop there. ProseMirror ignores the event too, since the block's view keeps it, so the listener puts the drop in itself with the code of the `handleDrop` prop, above or below the code block at its edge nearer the pointer, where the drop line shows, as for a table. Selected text goes in as a paragraph of its own there, as it does beside a table, rather than into the code. That keeps one rule for everything ProseMirror drags, and keeps a drop from mixing document text into code. Text dragged in from elsewhere, or within the code, is not in `view.dragging`, so CodeMirror still takes it at the pointer and shows its own drop cursor, and the drop line hides over the block. A file dropped on a code block goes in at the same edge as a block would.

A row or column handle takes no caret, so Chromium cleared the document's selection on a press there. When a drag of the handle moved no row or column, Crepe's drop put no selection back, and the next key went nowhere. Downpad's styles make the handles `user-select: none`, so a press there leaves the selection as it was. Crepe fades a table's handles with opacity once the pointer leaves the table or nears a cell border, and leaves them, with any menu open in them, where they were. A faded handle, and a menu open in it, shows again as soon as the pointer is over it, so the user sees it before a click there. A column menu sits over the paragraph above the table. Before the subclass closed a menu after a content change, a click there right after a Markdown edit of a cell in the split showed a menu whose selection was gone, and the click selected the column, so typing then replaced the column's text.

Each tab owns its own document state, including its path, content, save status, and line-ending style. The save status compares the content with the text last read from or written to the file, or with the starting text of a document that has no file. A recovered snapshot counts as unsaved until it is saved, because the file may have changed since. While a save is being written, any edit counts as unsaved, because the file may hold either text. When the save finishes, the document stays unsaved if its text or line-ending style changed while it was written, and a change on disk recorded in the meantime with a later time stays the file's text. A tab also counts as unsaved while files dropped on its document are on their way into it. The tab records that apart from the save status, so a save that finishes meanwhile does not clear it, and opening a file never reuses that tab. A dropped file only goes into a document that is in front, so a drop that also holds Markdown files puts its other files in before it opens the Markdown files. A new tab would otherwise put the document behind it, and the files would wait until the user showed that document again. If the user shows another tab before the files are in, they wait for their document anyway, so the Markdown files open at that point. Otherwise the Markdown files would wait with them and take the front when the user came back to the document. The active tab is bound to the visible editor views.

Milkdown and CodeMirror manage their own editor DOM and lifecycles. React owns the surrounding application interface, including tabs, toolbars, dialogs, settings, recent files, and print views.

The document view marks an image that fails to load on the image's element, and CSS draws the missing-image placeholder or chip from that mark, so it never reaches the document or its Markdown. Crepe reports load errors only for images on their own line, so Downpad catches the errors of inline images itself. After each change to the document a missing image shows its node's current path, and it shows as an image again once one loads there. Crepe's image views look a file up only when ProseMirror passes them their node again, so after the user locates the path an image already has, a node decoration that lasts one transaction makes ProseMirror do that without a change to the document. Chromium paints no text selection over a chip, so a ProseMirror decoration marks the inline images a selection covers and CSS tints those chips.

Crepe's image views render a node's raw src until Downpad's lookup of its URL answers, and Chromium would request a relative src next to Downpad's own page. That request fails, logs an error, and can show the image as missing for a moment. So the document view looks a document's local images up before its first render, and a pasted or dropped image stored as a file waits for the lookup of its file before it goes in (`lookUpImages`). Each wait lasts at most a second, so a slow file system cannot hold a document or an image back for long.

Chromium's End does not move the caret from before an image or a formula that starts a line. On End the document view first moves the caret past the inline atoms there, such as images and formulas, and Chromium's End goes on from the text after them. Chromium cannot keep the anchor of a selection right after a line break and before such an atom. Each time Shift and a key that moves the caret, such as End or an arrow key, extend the selection there, Chromium moves the anchor before the line break. The document view puts the anchor back when ProseMirror reads the extended selection, and has ProseMirror read it before the next frame, so the line break never shows as selected. It types over a selection that starts or ends there itself instead of leaving the typing to Chromium. It takes the text from the beforeinput event, which carries all of it, such as both halves of an emoji, and which also comes for text put in without a key press. An input method's composition cannot be cancelled, so when one starts over such a selection, the document view first removes the selection and the composition goes on from the caret that leaves. It does that in the capture phase, before Milkdown's own handling of a composition at a caret between two inline nodes, which works only when the caret is there as the composition starts. The same handler readies a selection that is not text, such as a selected block, selected table cells or a selected image or formula in a line. ProseMirror read the DOM selection as such a composition started, and over an image between two paragraphs the composed text went to the end of the paragraph above, with the image kept. So the document view first replaces a selected block or selected cells as a typed key does, but with no text, and the composition goes on from the caret that leaves, in an empty paragraph where the block was or in the cell where a key's text goes. It reads a move of the selection that ProseMirror has not read yet before that, as the ProseMirror patch does before text without a key. Chromium puts the caret after the composition's first text at the text offset where the selection started before the composition, plus the length of the text, and the replacement moved where that text goes. ProseMirror finds the composition's text from the caret, so with the caret elsewhere it drew the new text again, which ended the composition, and the next step started another one after the first text. A mutation observer that Chromium calls before ProseMirror's own puts that caret after the text first. A selected image in a line stays selected, and Chromium replaces it as it replaces selected text. ProseMirror reads that as typing over the image, which gives the text the image's marks, such as a link, as a key's text gets them. ProseMirror reads the browser's range around the image as it starts the composition, and it took that range for selected text, which the undo step kept. So an undo of the composition selected text instead of the image, and a composition cancelled after that removed the image. The document view has ProseMirror read that range as the image's selection while it starts the composition (`createSelectionBetween`). Chromium cannot replace an element that holds text, such as a formula's, so a formula gives way to a selected space with its marks, which the composition types over. Replacing either with a caret lost those marks, and between two images Milkdown's widgets beside the caret made ProseMirror draw the first step's text again, which ended the composition, so the text came in twice. When a composition ends at the end of a link's text, Chromium types a step that adds to the text of the step before, as Japanese input does, after the link's element. ProseMirror gives that text the link and draws it inside the link, which ends the composition, so the first step's text stays and the committed text comes after it, and a composition cancelled there keeps the first step's text. Chromium does that over selected text that ends a link, and the space that takes a formula's place ends the link when the formula does. So a formula at the end of a link's text, in a line or at its start or end, goes the same way, unless it is the whole text of a link that starts its paragraph, and a cancelled composition then leaves that text in the formula's place. Steps that replace the text of the step before, as Korean input does, stay in the link. Over a selected image Chromium keeps the later steps in the link, so an image does not use a space. The replacement starts an undo step, which the composition joins, so one undo brings the content back. A composition whose first text came more than half a second after it started would need two, but Chromium starts a composition and puts its first text in within one task. A composition that commits nothing, such as one cancelled, is taken back as soon as ProseMirror has read its end, in the same task, so no key, such as Ctrl+Z, and no other composition comes in between. The document view applies the inverse of the replacement and puts the selection back, and gives that transaction the history's state from before the replacement, found with Milkdown's key for the history plugin (`historyProviderPlugin.key()`). It does that when the document holds the nodes, text, marks and attributes the replacement left, apart from the ids of headings. Milkdown gives each heading an id from its text, with a number for a heading whose text an earlier heading has, and renames the headings as the document changes, also right after the replacement and as the composition ends. So replacing the first of two headings with the same text renamed the second, and a check of the whole document found it changed and left the empty paragraph. The same nodes and text keep the same positions, so the inverse still applies, and Milkdown renames the headings again after it. Any other change, such as an image's new file that an edit started before the composition put in meanwhile, leaves the empty paragraph and every undo step, so undo takes back that edit and then the replacement. Undo and redo are then left as they were before the composition, however the history grouped the composition's changes. The math delimiters' guard keeps a record for each undo and redo step of a typed closing `$` or `~` that waited, which the replacement cut back, and it takes a change that carries the history's meta for an undo. So the transaction also gives the guard its state from before the replacement, and redo puts back a formula that was undone before the composition as a formula, not as text. An undo would have kept the replacement as a redo step, so redo would replace the block with an empty paragraph again. The document view then closes the history, as an undo does, so the next edit does not join the edit before the composition. Crepe's code block view takes focus in its code when it is selected, as when a code block, a math block or a Mermaid diagram comes back, so the document view gives focus back to where it was, itself or another field. IBus ends each composition empty and then commits its text without one, a few milliseconds later. That text reaches the content that came back, and the ProseMirror patch types it over the content as a key does. With focus left in the code, that text went into the code instead.

Milkdown's link mark is inclusive, so ProseMirror gave text put in at a link's end, and at the start of a block that begins with a link, the link. Downpad keeps that schema, because typing over selected link text needs it to keep the link, and Crepe's virtual cursor handles marks that are not inclusive poorly. Instead, after every change, a plugin gives a caret at a link's edge the marks there without the link as its stored marks. ProseMirror reads stored marks first for typed text, an input method's composition, a paste and commands such as Ctrl+B, and the virtual cursor draws its tail from them. Crepe's list item views put the selection back a frame after they are drawn, which clears stored marks, and the plugin sets them again in the same update, so a link dropped as a list item needs no rule of its own. Deleting a link's whole text, with Backspace, Delete or Ctrl+X, stores the deleted text's marks for the caret, which then sits inside the text around the link, so the plugin also takes a stored link off a caret that neither side of it carries. The plugin also tracks a link side, where typing goes into the link. The virtual cursor's Left at a link's end where text follows, and its Right at the start of a link that follows other text, set the link as stored marks without moving the caret, and typing over selected link text keeps the link. Each puts the caret on the link's side. Typing there keeps it there while the caret stays in the same text block, and so does Backspace or Delete that takes some of the link's own text, because ProseMirror gives the caret's next text the deleted text's marks. A move of the caret ends it. So does deleting the text on the other side of the caret, or the link's whole text, which leaves no link beside the caret in the marks its next text gets, and the virtual cursor then draws the tail on the plain side. Stored marks stay in the state while the caret rests at a link's edge, so find and replace clears them before it replaces a match, and text the browser changes away from the caret, such as a spelling fix, gets the marks of its own place. ProseMirror gives plain text that is dropped the marks of the place under the pointer, and the drop then puts the text in a block of its own at a block edge, so text dropped on a link became a new link to the same target. The plugin takes links off plain text that is dropped or pasted. A paste at the caret gets the marks there again, because Milkdown's paste reads stored marks. A file dropped right before a link to the same target, such as a missing attachment that the file fills, joins that link, so the caret after the file is inside one link. The drop makes that caret a plain caret, which the plugin tracks as it does the link side. The plain caret follows the caret while the caret stays where the edits map it, as typing, Backspace, Delete, undo and Milkdown's change of a heading's id after each edit of the heading do. Inside a link, it gets the marks there without the link as its stored marks, as a caret at a link's edge does. Stored marks alone did not last, because ProseMirror drops them on every change, and after Backspace or Delete gives the caret's next text the deleted text's marks. A link side ends a plain caret, and a drop ends a link side. The URL shown after a link is drawn before a caret at the link's end, where the next character goes, unless that character joins the link, as on the link's side. It is drawn after a selection's end at the link's end. Drawing the URL before a selection's end made Chromium type over the selection outside the link's element, which ProseMirror read as taking the link off the retyped text.

The URL after a link is CSS generated content of a widget element that holds only an empty comment, with no text in the DOM. For a plain click or Shift+click, ProseMirror leaves the caret where Chromium puts it and reads it back. Chromium has no caret position inside text that can be neither edited nor selected, such as a widget's text. For a click on such text it falls back to the start of the element under the pointer, which was the paragraph, because the URL takes no pointer events. Chromium puts a click on generated content after the widget instead, which ProseMirror reads as the link's end. The comment keeps an input method working right after the URL. Chromium treats a non-editable element with no children as one solid object, and with such an element a composition of more than one step went in twice, because Chromium dropped the composition and then put its committed text in as plain typing. With text in the element, even a zero-width space, Chromium lost the caret when a composition there was emptied, and the next one went in at the start of the paragraph. Because the URL is not text, word movement and deletion, such as Ctrl+Backspace, Ctrl+Left or a double-click, treat a link and letters typed right after it as one word, as they do when only the link text is shown. Print breaks a paragraph or heading only between the lines of its text, so the print copy writes the URL into the element as text and drops the attribute the generated content comes from. A heading whose URL wraps past a page then continues on the next sheet instead of being shrunk onto one.

Downpad opens a link on Ctrl or Cmd+click. ProseMirror selects the innermost block under the pointer as a node on a click with Ctrl, or Cmd on macOS, and the block around that on the next such click, so a Ctrl+click beside a link selected the whole paragraph or list item and the next key replaced it. The link plugin therefore takes every Ctrl or Cmd+click that reaches it and gives it the selection a plain click gets. Taking the click makes ProseMirror cancel the browser's handling of the release. Chromium keeps a selection that a press lands inside, because the press could start a drag, and puts the caret at the click only on the release. The plugin therefore puts the caret at a click inside the selection itself, such as in selected text, a block the block handle selected or the whole document. A selection with a hidden caret, such as a node or cell selection, gives way to a caret at a click next to it, as ProseMirror does for a plain click, because Chromium can report no change for a click at that hidden caret. Elsewhere the caret stays where Chromium put it on the press. A click that opens no link also selects a leaf node under the pointer, such as an image. One that opens a link leaves the image unselected and puts the caret at the side of it clicked, so the next key cannot replace the image. Chromium puts no caret on an image, so without that the selection from before stayed, and the next key replaced it. The plugin focuses the view only after it sets the selection. While a code block has focus, ProseMirror's selection stays in the block, and focusing the view first puts the browser's selection, and focus, back there. The URL after a link takes no pointer events, so a click on it targets the block around it, and the plugin finds the URL under the pointer by its box. The URL's widget sits right after the last character of its link, so that character names the link to open, never a link that follows. ProseMirror finds the link's end under the pointer on the URL, so a caret the plugin puts at such a click goes there, as a plain click's does. Crepe's link preview found its link from the position under the pointer, which on the right half of a character or on the URL is the position after it, where a link that follows starts. Downpad's patch of `@milkdown/components` has the preview take its link from the element under the pointer instead, as the click does. The preview's Edit and Remove act on a range, which Crepe took from the one node it found. A link of several nodes, such as an image with a caption after it or text around bold text, was then split, and Remove left the link on the rest. The patch gives them the run of nodes around that node that carry the same link mark, which the document view shows as one link, with one URL after it. Such a run can also be two links to the same address with nothing between them, such as `**[ra](z)**[rb](z)`, because the document does not tell those apart from one link of several nodes. Edit and Remove then change both together.

Each code block is a CodeMirror editor, which handles its own clicks and adds a cursor on Ctrl or Cmd+click. A block that does not have focus keeps the cursor it had, at its start unless it had focus before, so a Ctrl or Cmd+click from outside the block added a second cursor there, and typing went in at both. Downpad gives Crepe's code blocks a `clickAddsSelectionRange` extension that adds a cursor only in a block that already has focus. CodeMirror also selects from that cursor to a Shift+click, so from the document, the Markdown pane or another code block, the next key replaced the code from the block's start, or from where its cursor last was, to the click. A Shift+click from the document pane into the split's Markdown pane did the same to the Markdown. Downpad's CodeMirror press extensions, which the code blocks and the Markdown view both use, therefore first put the cursor at a Shift+press in an editor that does not have focus, so the selection from there ends at the click, as a plain click's caret does. CodeMirror handles presses on its content only. A press on a gutter went to the browser. On a line number or a fold arrow, Chromium focused CodeMirror's scroll container. That takes no keys, so the next key was lost. On a Shift+press in the fold gutter's blank space beside a line, Chromium extended the selection to the start of the text, and the next key replaced the text in between. The extensions put the cursor at the start of the line of a pressed line number and focus the editor, or extend the selection to there on a Shift+press while the editor has focus. They cancel a press on another gutter beside a line, such as on a fold arrow, so focus and the selection stay where they were, and CodeMirror still folds or unfolds on the click. In the Markdown view, a press on any gutter below the last line puts the cursor at the end of the text instead, as CodeMirror does for a press below the last line in the text beside it, and a Shift+press there while the editor has focus extends the selection to the end. The gutters there reach down to the bottom of the editor, so that covers the gutters below the end of the Markdown. CodeMirror's fold gutter takes a click below the last line for one on the last line, which unfolded a folded section that ends the Markdown, so the handler stops such a click before it reaches the gutter. In a code block, the gutters reach only a few pixels below the last line, beside the code's bottom padding, and a press there counts as one beside the last line.

While a code block has focus, the document view's selection is inside the block, and focusing the view puts the browser's selection, and focus, back into the block. ProseMirror focuses the view before it selects what a click selects, and Crepe's block handle focuses it before its + button puts in a paragraph. So a click from a code block on an image on its own line selected the image, and the + button put the caret in the new paragraph and opened the block menu there, while focus stayed in the code block, and the next key went into the code. Whenever the document's selection is no longer in the code block that has focus, Downpad focuses the document view, so focus goes where the selection is.

Crepe's block handle selects its block and focuses the document view on a press. The handle lies outside the view and takes no focus, so Chromium's own handling of the press then moved focus to the page. Crepe focuses the view again only on a release on the handle itself. A drag that moved the block focused the view at the drop, but a drag cancelled with Esc, dropped back where the block was or dropped outside the document left focus on the page, and the next key was lost. Chromium starts no drag on a Shift+press, which it takes as extending a selection, so a Shift+drag on the handle only selected the block and lost the next key too. Cancelling the press would keep focus but stop every drag. Downpad instead focuses the view once a press on the handle ends, on the release or at the end of its drag, unless something else has taken focus by then, such as the Markdown pane after a drop there. The block the press selected, or the block the drag moved, is then selected, so the next key replaces it. The drop sets that selection before it focuses the view, where ProseMirror's own drop focuses first. A code block's view focuses its code when the block is selected, so a moved code block kept focus in its code, and the next key went into the code instead of replacing the block, as it does after a click on the handle.

Crepe moves the handle to the block under the pointer on a pointer move over the document view, at most every 200 ms. After the view changed width, as on a switch from the Document view to the Split view, the handle stayed where it had been, which could be over a list item's bullet or a task's box. A pointer move over the handle is not one over the view, so it left the handle there, and a click on the bullet or box selected the handle's block, which the next key replaced. Crepe also slid the handle to each new place over 0.2 s, and the handle took clicks on its way. Downpad hides the handle whenever the view's width changes, which a ResizeObserver reports, and its styles have the handle appear in its new place at once and only fade in. The observer reports the change before the browser draws the new width, so from the first frame that shows it the handle takes no press. A press sent before that frame, which only automation such as a test can aim at the new layout, still reaches the handle. Either change alone left the bug. Without the hiding, the click landed on the handle where it had been. Without the change of style, the pointer move that comes with the click showed the handle, which then slid from where it had been and took the click on its way.

Crepe draws a list item's bullet or number in a label outside the item's text. Chromium puts the caret of a click there at the nearest place for one, which for a number, a run of text, is the start of the item's text. A bullet is a drawing with no such place near it, so Chromium put the caret at the start of the document, often out of view. While a code block had focus, focus stayed in the block, its cursor went to the end of the code, and a Shift+click selected the code to there. From the find card or the Markdown pane, a Shift+click focused the document without a caret, and the next key was lost, and with cells selected prosemirror-tables took it, kept a cell selected and kept focus outside. Downpad's list label plugin takes a press on a bullet or number in the capture phase, before ProseMirror and prosemirror-tables see it. It puts the caret at the start of the item's text, focuses the view, and follows the pointer during a drag, as the Shift+click plugin does. A Shift+press while the view has focus extends the selection to the start of the item's text instead. A task's box toggles the task on the press, which Crepe's view handles and cancels, so no mouse events follow it. Crepe focuses the view first and leaves its selection as it was. While the view has focus, that is the selection the user sees, and it stays. From outside the view the user does not see it, so the next key replaced text selected there, possibly out of view, and from a code block focus went back into the block and the next key replaced the selected code. On a press on a task's box from outside the view, the plugin therefore first puts the caret at the start of the task's text and focuses the view, before Crepe toggles the task.

Chromium does not extend the selection on a Shift+click whose press lands on a link or an image, even in an editable element. On a link it puts the caret at the click, and a Shift+drag from there starts a new selection at the press. On an image it leaves the caret where it was, and a Shift+drag moves the image. ProseMirror leaves Shift+click to the browser, so Downpad's Shift+click plugin handles a Shift+press on link text or on an image inside a line of text itself. It selects from the selection's anchor to the position under the pointer, or to the side of the image pressed, and then follows the pointer until the button is released. Beside a block's text, such as in the document's side padding, left of a list item's or a quote's text or in a table cell's padding, ProseMirror's `posAtCoords` gives the position before or after the block. A drag that followed it there selected to the start or end of the whole block, or to the end of the block before, while Chromium's own drag selection takes the line at the pointer's height. The plugin therefore follows the pointer to the text block nearest it, found as for a press in the side padding, and to the position ProseMirror finds at the pointer moved into that block's lines, which beside a line is the line's start or end. The point goes between the top of the first line and the bottom of the last, not only into the block's box, because the box can hold padding below the last line, where Chromium on Linux and macOS puts the caret at the line's end whatever the point's x. Below the last block, in the view's bottom padding, the selection runs to the end of the document instead, where a press there puts the caret. The children of a block lie in order down the page, or side by side in a table row, so a binary search finds the nearest one. ProseMirror finds a child's element by counting from the first child, and measuring every block of a document with thousands of blocks took longer than a frame on each move. The anchor stays where the press found it, also when another plugin changes the selection in between. prosemirror-tables turns a selection that ends at the start of a cell into one of the paragraph it starts in, and an anchor taken from that selection stayed at the paragraph's start for the rest of the drag. A change to the document moves positions, though. Such a change can be a key pressed while the button is down, such as Backspace, or one made along with the selection, such as a typed closing `~~` that becomes strikethrough once the press takes the caret away from it. The drag then goes on from the anchor of the selection, which ProseMirror moved along with the change. After Backspace it goes on from where the key left the caret, as Chromium's own Shift+drag on other text does. While the pointer is above or below the document's scroll container, the plugin scrolls the container each frame by as far as the pointer is outside it, as Chromium's drag selection does, and extends the selection to the container's edge. prosemirror-tables handles the press before the plugin and selects cells on a Shift+click into another cell or while cells are selected, and the plugin stops following a drag once the selection is no longer a text selection, as when prosemirror-tables selects the cells the pointer crosses. While the document view does not have focus, such as when a code block, the Markdown pane or the find card has it, the selection to extend is not the one the user sees. Chromium extended the selection of the code block or the Markdown pane toward the click, which CodeMirror cut off at its start or end, and focus stayed there, so the next key replaced the code or Markdown between the caret and that point. On an image Chromium put no caret, and the next key went into the editor that had focus. prosemirror-tables decided from that selection too. A caret left in one cell made a Shift+click into another cell select both cells, and a cell selection made a Shift+click anywhere in the document select a cell. It cancelled the press, so focus stayed outside and the next key went in there. While the view does not have focus, a second plugin, which Downpad puts before all other plugins, therefore takes any Shift+press on the document's text or on an inline node such as an image. It puts the caret at the press, or at the side of the node pressed, and then focuses the view. Focusing the view first would move focus back into a code block that holds the selection. The press then goes on as one in the focused view with the caret at the press. prosemirror-tables finds that caret in the cell pressed and leaves the press alone, the Shift+click plugin extends the selection from it on link text or an image, and Chromium does on other text. Chromium extends it to the point where a plain click puts the caret, so the plugin's caret has to be at that point too, or the next key replaces the text between them. For a press beside or below a block's text, such as in a table cell's padding right of or below its text, ProseMirror's `posAtCoords` gives the position before or after the block, while Chromium puts the caret in the nearest text. The first caret after the end of a cell is in the next cell, so prosemirror-tables selected the cells from there to the one pressed, and the next key replaced their text. After a table's last cell it was past the table, and Chromium extended the selection back over the cell's text. Left of a cell's text and below its last line, ProseMirror's position is before the paragraph while Chromium on Linux and macOS puts the caret at the end of the line, so the next key replaced the cell's text. On Windows, Chromium puts it at the point of the line nearest the click. For a press whose position is between blocks, the plugin therefore puts the caret where `caretPositionFromPoint` finds Chromium's caret, read as ProseMirror reads the caret of a click. A Shift+drag from there therefore selects from the press, and selects cells across a table, as a plain drag does. A Shift+press from outside on any other part of the document is a plain click there. Such parts are a code block's toolbar, edges and preview, which keep their events from ProseMirror, a rule, an image on its own line and the table's handles. Chromium extended the selection of the editor that had focus toward such a press too. From the Markdown pane the next key replaced the Markdown from the pane's start to its caret, and from the find card Chromium focused the document at its old caret, where a plain click on a code block's toolbar puts the cursor at the end of the code. Chromium extends only a selection there is, so once a Shift+press's handlers have run, a listener on the whole window drops the browser's selection, and Chromium handles the press as a plain click. It leaves the selection when a handler cancelled the press or moved focus, as the plugin does for a press on text, and when the element that has focus holds the press. The listener also leaves a selection in text that cannot be edited, such as a read-only value in the frontmatter table, which Chromium extends as on any page, also when nothing has focus. Chromium reports the selection of a focused text field, such as the find card's, at the field's place in its parent element rather than in text, so that selection is still dropped. The listener covers the rest of the window too. A Shift+click into a cell of the frontmatter table from the document or the Markdown pane puts the caret at the click, and one on the empty part of the tab strip from the Markdown pane is a plain click there. Chromium extended the selection of the editor that had focus to its start in both cases. ProseMirror still sees the Shift key, so where ProseMirror decides what a plain click selects, the plugin does it. It selects a rule or an image on its own line and then focuses the view, and it gives up a cell selection for a caret in the cell of its head, so prosemirror-tables leaves the press alone. The plugin extends the selection by characters. After a double-click selects a word, Chromium extends the selection by whole words. A page cannot read that state, so a Shift+click on link text then ends at the click. Because the plugin takes the press from ProseMirror, a Shift+double-click on a link to a Markdown file extends the selection instead of opening the file.

A press on the page around the editors, such as beside the document's column, in a split pane's margin or below the end of the document view or the Markdown view, lands on no editor. Chromium moved focus to the page there, and the next key was lost, also when the document had focus. A Shift+press there from the Markdown pane extended the pane's selection to its start. A listener on the editor area cancels a press whose target holds an editor, the document view or a CodeMirror editor, but lies outside it, so focus and the caret stay where they were. A press inside an editor, or on another element such as the frontmatter table or the split's divider, is left as it was. The frontmatter table cancels a press beside its keys, values and buttons itself. Below the end of the editor that the document's column or a pane shows, most editors put the caret at the end, so there the listener also sends the editor a copy of the press at the same point, with the same button, keys and click count. The copy goes to the document view itself or to a CodeMirror editor's content. It does not bubble, so of the listeners around that element, such as the editor area's own and the one for Shift+presses, only those for the capture phase see it. The editor ends where its content ends inside its padding, which for the document view is the bottom of its last block. The document view takes the copy as a press below its last block, as described below, and CodeMirror puts its cursor at the end of the text for any point below its last line, follows a drag and extends the selection on a Shift+press, as in its own box. A press on the editor area itself, beside the document's column, keeps focus where it was at any height. The column runs to the bottom of the window for a short document, so the page beside it shows no line where the document ends. In the Markdown view, the editor fills its pane, but its text and gutters stopped at the last line, so a press below them landed on CodeMirror's own element. Chromium put the cursor on the last line there, at its end on Linux and macOS but at the point nearest the press on Windows, and below the line numbers it moved focus to the page, so the next key was lost. The text and the gutters now reach down to the editor's bottom, so a press below the last line lands on CodeMirror's text, which puts the cursor at the end, or on a gutter, where Downpad's handler for gutter presses does the same. CodeMirror's theme gives the gutters a height of 100%, which kept them from stretching, so Downpad gives them an automatic height. Only the room find adds below the Markdown view in the Markdown layout lies outside the editor, and the listener hands a press there on to the text.

Crepe pads the document view on each side, and a press in that padding lands on the view's own element. ProseMirror leaves a plain press to Chromium, which puts the caret on the line pressed beside a paragraph or a heading. Beside a block that is not editable text itself, such as a code block, a math block, a Mermaid diagram, an image on its own line, a table, or a list item, whose bullet comes before its text, Chromium put the caret before or after the whole block, by the half of the block pressed, and then moved it to the nearest place for a caret in the order of the page. That was the end of the text before the block, the start of the text after it, or the start of the document. Beside a code block at the start of the document, the caret went into the code at its start, or, with text selected, nowhere, and the next key was lost. Downpad's padding plugin therefore takes such a press in the capture phase and cancels it, and ProseMirror and its plugins leave a cancelled press alone. The plugin descends from the document through the block nearest the press at each level, by height first and then across, such as through a list, its item and the item's paragraph, or through a table, its row and the row's first or last cell. It ends at a text block, a code block or a block that takes no caret. In a text block it puts the caret where ProseMirror finds a point at the block's edge at the press's height, which is the start or end of the line, and follows the pointer during a drag, as the Shift+click plugin does, to the line beside the pointer or the text under it. It finds that line as it finds the press's, so a press that moves a pixel or two stays a caret. In a code block it focuses the code with CodeMirror's cursor at the start or end of the line at that height. CodeMirror gives the first or last line for a height above or below the code, as beside the toolbar or the preview. CodeMirror follows a drag only from a press on its own text, and Chromium follows none from a cancelled press, so a drag from beside the code selected nothing. The plugin therefore follows such a drag itself and selects in the code from the cursor. While the pointer is in the side padding, the selection runs to the start or end of the line at the pointer's height, and elsewhere to the position CodeMirror finds for the pointer in a drag in the code, which is the code's start or end above or below the code. The plugin scrolls the document as the Shift+click plugin does, and stops on release, when the window loses focus and on Esc, which collapses the code's selection that the next move would otherwise select again. A code block whose code is hidden, as when its preview shows alone, is selected as a whole instead, as its handle selects it, and so are a rule and an image on its own line, as a click on them selects them. A press beside the lines of a paragraph or a heading at the top level stays with Chromium, which places it right and keeps its own double-click there. A Shift+press while the view has focus extends the selection from its anchor to the line's start or end. Beside a code block, an image or a rule, and from outside the document, a Shift+press is a plain one, as on those blocks themselves. So it is while a block, such as an image on its own line, or table cells are selected. The anchor of such a selection is not in text, and a text selection from there starts in the text after it. The selected image was left out, and with a table after the image the selection started in the table's first cell, so the next key broke the table up. From selected cells the selection started in the cell where the cell selection ended.

A press in the view's bottom padding, below its last block, lands on the view's own element too. Chromium put the caret on the last line, at its end on Linux and macOS but at the point nearest the press on Windows, and left of the text column the padding plugin put it at the line's start. On the page below the view, the editor area's listener kept focus where it was. The padding plugin therefore takes a press below the last block, in the bottom padding or handed on by that listener, and puts the caret at the end of the document, ProseMirror's `Selection.atEnd`, on every platform. The last block ends where the view's bottom padding starts, which the plugin and the listener measure the same way, so the plugin takes every press the listener hands on. Crepe's trailing plugin keeps an empty paragraph after a last block that is not a paragraph or a heading, such as a list, a quote, a table, a code block, a math block, a Mermaid diagram, an image or a rule, so there is a line to type on, and puts it back after any change that removes it. The end is therefore always the end of a paragraph or a heading. After any other block it is that empty line, where the next key starts a new paragraph, so it never replaces a block or goes into one, also beside a block that takes no caret or a code block whose code is hidden. A gap cursor after such a block, which Crepe's cursor feature could show, is not needed. A drag from there selects from the end to the pointer, and to the end while the pointer stays below the last block, so a press that moves a pixel or two before the release only puts the caret. A Shift+press extends the selection to the end while the view has focus, as beside a line, and is a plain one from outside the document or while a block or table cells are selected.

Crepe's selection toolbar decides whether to show only when the document view updates, and a move of focus is none. After text was selected in the document and a click moved focus to the split's Markdown pane, the toolbar stayed over the document, covered the text under it and took clicks, which formatted the document's selection while the next key went to the Markdown pane. Downpad hides the toolbar when the view loses focus to anything but the toolbar. Crepe shows it again on the next change of the selection while the view has focus.

Mermaid fences load Pele on first use through Crepe's code-block preview hook. All preview requests await the same import and render synchronously, so a slower diagram-type download cannot overwrite a newer edit. Each SVG gets a unique identifier prefix, and CSS variables map its colors to the document palette or the light print palette. Theme changes need no redraw. Diagram links stay inert, and parser errors are displayed as text.

Markdown-looking clipboard text is intercepted in the DOM paste handler before Crepe's clipboard plugin. Downpad splices it into the source at the selected body position, parses the resulting frontmatter and body, and records their source baseline in the same undo transaction. A temporary text marker maps partial selections through the existing baseline-aware serializer. Untouched blocks keep their source, and the surrounding changed block follows normal document serialization. Clipboard text uses the file loader's BOM and line-ending normalization. Inline code receives literal text, and a selected table rectangle receives cell contents while retaining its existing header and body cell types.

## Interface design

The interface follows the look of [Mervin PDF](https://github.com/lincarl/mervin-pdf). Dark mode uses Mervin's "Nord" chrome and light mode its "Cool slate" chrome.

- `src/styles/app.css` defines the chrome tokens (surfaces from the input well to the floating popover, inks, translucent edges and washes, the accent) for both themes and exposes them to Tailwind as colors such as `bg-well`, `text-ink-soft` and `border-line-push`.
- The primitives in `src/components/ui` (buttons, fields, check boxes, dialogs, menus, tooltips) carry Mervin's control styles, so surfaces compose them instead of restyling controls.
- Chrome icons are Lucide icons drawn at a 1px line weight.
- Recent sits immediately left of Open in the menu row, using the toolbar button style and Lucide's `list-clock` icon. Its pressed state marks the Recent view. Recent, Open and Save hide their labels together in narrow windows.
- General settings uses the existing select and check box controls for the default Recent search and whether missing files remain listed. Below 700px its labels and fields stack to fit the narrow window. Missing entries are filtered before the visible-row limit, leaving room for available files. History stays intact, and metadata from an older refresh cannot replace the current refresh's results.
- The document page keeps Crepe's 120px side padding while the text column can stay at least 400px wide. In a narrower editor, such as the Split view's document pane in an 800px window or the Document view in a 600px window, the padding gives way, down to 58px on each side. With the 24px the page or the pane adds around the editor, that still holds the block handle, which is 66px wide and sits 16px left of the text. CSS works the padding out from the editor's own width, so it follows the window, the split divider and the page width setting. With the default page width the Document view looks as before in windows 1000px and wider. A fixed page width below 688px narrows the padding in every window, so a 600px page has a 400px text column where it had 312px.
- The window's rows, from the toolbar to the status bar, share one grid column that is exactly as wide as the window, so no row can make the others wider. A row with more content than fits shrinks or cuts its own content. The status bar ends a path too long for it in an ellipsis, and its tooltip has the whole path.
- The document surface has its own light and dark palette, independent of the chrome theme. Dark documents use a `#040404` background with `#d4d4d4` body text and retain the existing VS Code Dark+ syntax colors in Markdown view. Find highlights use the same classes in the Document and Markdown views. The frontmatter table is outside the document editor, so its matches are CSS custom highlights with the same names and colors.
- The find card floats over the bottom right of the editor area and grows upward when its replace row opens. In a window too narrow for the card's top row, below about 610px, the card spans the editor area, less 12px on the left and 24px on the right, and Match case and Whole word move to a line of their own under the find field. The fields keep their width, and Close stays at the top right, so every control stays inside the editor area down to the narrowest window, 480px. Each find step scrolls the current match into view clear of the card, at whatever height the card has, centring it in the part of the page above the card when it was hidden or covered. When the end of a document stops the page short of that, the page gets room below its last line, as tall as the card reaches up into the page plus 12px, until the card closes. Find measures a match that wraps onto more lines by the box around all of its lines, not by its two ends alone.

## Application structure

The frontend is organized around a small observable application store and service modules for the major responsibilities:

- Document and tab state.
- File operations and external-change handling.
- WYSIWYG and source-editor integration.
- Paste, image, attachment, and link handling.
- Recent files, search, settings, and recovery.
- Printing and platform integration.

The Electron main process provides operations that require native access. File reads and writes, attachment storage, recovery snapshots, recent-file data, and settings persistence stay outside the renderer. A bundled preload exposes typed operations through Electron's context bridge. The renderer uses context isolation and sandboxing without Node.js access.

Packaged builds always load the bundled frontend and ignore development URL overrides. Unpackaged development launches accept only HTTP or HTTPS URLs on localhost, 127.0.0.1, or ::1, without credentials. Native commands accept only the authorized main frame.

The built frontend carries a Content Security Policy, defined in `vite.config.ts`. It blocks inline scripts, eval and scripts from the web, and allows images from the web, data and blob URLs, and local files. The development server goes without it. A feature that needs a new kind of resource, such as a frame or a web font, must add it to the policy.

## Data and persistence

User documents remain standard Markdown files. Downpad does not use a proprietary document format.

Application preferences are stored in `settings.toml`. Recent-file history and recovery snapshots are stored separately in the application's local data directory. File writes are performed atomically where practical to reduce the chance of corruption.

The open documents are kept in `session.json` as the files of the tabs, in order, and the active tab's file. The renderer writes it whenever that list changes, and the close guard waits for the write before it closes the window (`SessionKeeper`), so a crash leaves the latest list too. Startup reads it before it clears the tabs, then reopens the files after recovery and before a launch argument (`StartupCoordinator`, `FileService.restoreTabs`). Files that startup cannot read stay in the saved session, with their order and active preference, until they become available or every visible tab is closed. Recovery and an explicit launch file take active priority. A manually reopened file returns to normal tab tracking, so a later close or Save As does not restore its old path. The reopened tabs are filled from disk without building their editors, so only the active tab builds one at start, and reopening does not count as opening the files for the Recent view.

Recovery uses each tab's UUID in the existing snapshot `sessionId` field, keeping the same JSON format and reading older snapshots unchanged. The scheduler refreshes every dirty tab at each recovery interval and deletes only the snapshots of saved or closed tabs. It orders operations for each tab, retains failed operations for retry, and waits for dispatched writes before clearing snapshots on shutdown. Cleanup failure cancels shutdown and resumes recovery. The existing retention period and limit of 50 readable snapshots still apply across sessions. Files that cannot be read remain untouched for a later attempt, so temporary filesystem errors can leave more than 50 files on disk.

Settings saves use TOML syntax-tree ranges to update complete root values and insert missing settings before the first table. Quoted keys, surrounding comments, unknown data, a leading BOM, and existing line endings are preserved. Settings reads reject invalid UTF-8 rather than replacing bytes, and loading failures use defaults without changing the file. Before writing, the app checks that the result parses and contains exactly the requested settings plus the original unknown values. Invalid UTF-8, invalid TOML, or known settings expressed as dotted keys or table declarations remain untouched, and the app reports that saving failed. Known settings must use root key-value assignments.

Images can either live inside Markdown as data URIs or as files in a configurable attachments directory. Relative paths are used for attachment links so a document and its attachments can be moved together. A pasted or dropped file is written beside the document as it is saved when the file is written, because the user can save the document in another folder while a large file is read or written. FileService gives a document its new path only once a Save As has written it, so the paste or drop first waits for any Save As of its document that is under way (`FileService.untilPathSettled`). Before that it waits for the pastes and drops into the document before it to end (`EditorHost.untilTurn`), because its file goes in only after theirs. So a file is not stored and then held back while the user saves the document in another folder. If the document still moves to another folder while the file is written, the file is written again beside it. Its link then leads from the document's own folder, which always resolves and moves with the document, unlike a link back to the old folder, which cannot reach another drive. Pasted, dropped and uploaded images stored as files, an image chosen with Replace image, and other dropped files all go through this loop (`storeBesideDocument` in `src/images/imageStore.ts`). The lookup of a new image's URL (`lookUpImages`) runs inside the loop, before the check for a move, so a Save As that ends during the lookup writes the image again and looks it up again. An embedded image does not depend on the document's folder, so it skips the loop and never waits for a Save As.

A pasted image goes in through the same code as a dropped file (`FileDropCoordinator.pasteImages`), at the block edge at the caret, which is fixed when the image is pasted and which the document pane keeps in step with edits (`WysiwygEditor.caretTarget`). In a table, that edge is above or below the table, where the image goes in (`blockEdge`). An image pasted later at the same edge maps past the ones that went in there. Where an image takes an empty line, such as Crepe's last line below a final table or code block, it goes in before the line, which is then taken out, so a later target at that edge still maps past it. The files of a drop or paste also go in only once every drop or paste aimed at the same document before it has ended (`EditorHost.untilTurn`). Otherwise a later image that was stored first would go in first, and the earlier image, whose target maps past it, after it. So a file waits for a slow file dropped or pasted into its document before it, as the files of one drop do, and a drop's Markdown files, which open once its other files are in, wait with them. A file that goes in at a caret has no target that maps past earlier files, because the caret can stay before them. The files of one drop follow each other from the place after the one before. When a drop ends, it hands the place after the files it put in at a caret to the next drop of the document that is under way (`AimedDrop.follows`), whose files go in there while their own place is gone. That chain ends once no drop of the document is under way. EditorHost holds the image while its document is behind another tab, and counts the tab as unsaved until it is in (`Tab.filesPending`), as for a drop. Milkdown's clipboard plugin takes a paste that holds HTML or plain text, also when it holds an image too. An image alone on the clipboard, such as a screenshot, would reach Crepe's upload plugin, which stores it through the image block's upload hook and then puts it into the editor that took the paste. By then that editor can be rebuilt for an edit in the Markdown view, or dropped from memory behind another tab, which loses the image although its file was written. The upload plugin also puts in an image without a src when the save that an untitled document needs is cancelled, because the hook cannot cancel it. So Downpad's paste plugin takes such a paste in a DOM event handler, which ProseMirror runs before any plugin's `handlePaste`, and hands its images to the app (`WysiwygContext.pasteImages`). An editor built without that hook, such as the one print renders with, puts a pasted image nowhere.

A pane that a layout switch hid still takes a dropped or pasted file at its place while it holds the document's latest edit (`EditorHost.usable`). The document pane behind the Markdown view inserts the file and gives the Markdown view the matching change to its source (`insertMarkdownWithSource`), as the split does while the user types in its Markdown pane. The Markdown view's report of that change makes the tab's text newer than the hidden pane's, so Downpad then mirrors the text into the hidden pane, as the split mirrors it into a pane on screen (`EditorHost.mirrorInto`). The pane holds that text already and stays as it is, but counts as up to date again, so the drop's next file, or an image pasted after it, still goes in at its place. A mirror leaves a document pane's blocks alone while the pane's document is still the one the text gave it (`WysiwygEditor.setMarkdown`). The parse of the text can hold a block another way than the pane does, such as a list item with an image, which the text reads as loose and the pane holds as tight. Replacing that item would move the places of later files in it to its end. A change that any hidden pane of the document shown reports goes into the pane shown at once (`EditorHost` `onChange`). Without that, the pane shown would lag the tab's text, and `onChange` would drop its later edits as stale, so typing that stays on screen would be left out of the save. That also covers the image block's upload input and Replace image, which put the stored image into the editor that asked for it, even when a switch to the Markdown view hid it meanwhile. That editor reports the image after its usual pause, about 200 ms, so an edit in the Markdown view during the pause leaves the image out, and the edit stays. Once the hidden pane is behind an edit, or after a reload or a rebuild of the view, a file goes in at the caret of the view being edited. In the Markdown view, a file aimed at the document view then goes in as a paragraph of its own after the top-level block that holds the caret (`RawEditor.blockTargetAtCaret`), so it never joins the line the user types in, a heading, or the frontmatter, and never goes between the lines of a formula. Where that block is the last one and takes in text after it, such as a code fence or a formula that is not closed yet, the file goes in before it. A file that goes into the Markdown view is an undo step of its own there (`isolateHistory`), because CodeMirror joins a change without a user event to typing next to it within half a second.

The image block's upload input and Replace image put an image into the editor that asked for it, so they do not wait for a Save As (they leave out `ImageStoreContext.untilPathSettled`). A long wait would make it likelier that the editor is rebuilt or dropped from memory before the image goes in, which loses the image. They still write the image again if a Save As that ended while the image was written put the document in another folder. A Save As still being written when such an image is written leaves the image beside the old folder, with a link that does not resolve from the new one.

Attachment writes stage complete bytes in a sibling temporary file before publication. On filesystems with hard links, publication atomically claims a free name. FAT and exFAT use serialized application writes, a fresh name check, and atomic rename instead. That fallback preserves support for these filesystems, but another process creating the same name between the check and rename can have its file replaced.

## Desktop integration

Electron provides native windows, file associations, single-instance behavior, native open/save dialogs, opening links and folders, system appearance settings, and printing. Linux builds provide AppImage and DEB installers. Windows builds provide MSI installers.

Downpad was called md-easy before. The installers and the app take over what an installed md-easy left:

- MSI major upgrades schedule removal after `InstallInitialize`, so Windows Installer can restore the previous version if the new installation fails.
- The MSI keeps md-easy's upgrade code, `msi.upgradeCode` in `package.json`, so it replaces an installed md-easy. Without it, electron-builder derives a new code from the new app ID, and Windows would keep both apps.
- The MSI also keeps md-easy's ProgIds for Markdown files, `mdeasy.md` and `mdeasy.markdown`, which `scripts/brand-msi.mjs` puts in place of the ProgIds that electron-builder derives from the product name. A default app chosen for .md files names its ProgId, so a user who made md-easy the default keeps Downpad as the default.
- The DEB package conflicts with and replaces the `md-easy` package, so installing it removes md-easy. It also installs `build/linux/md-easy.desktop`, which is hidden from menus and opens Downpad, because a default app chosen for md-easy names that file.
- The app moves the settings, recent files, window size, recovery snapshots and the words added to the spell checker from md-easy's data folder to its own (`adoptLegacyData` in `electron/storage.ts`). It moves each file on a launch where its own folder lacks that file, so it never replaces Downpad's data. A file that can be neither moved nor copied stays in the old folder and is tried again on a later launch, unless Downpad has made its own by then, as it does with its settings and recovery folder at startup. Chromium's other files stay in the old folder. After it takes over md-easy's settings, it checks once more on Windows whether it is the default .md app, as on a first launch, because a default chosen as md-easy's executable no longer exists.

Undo and Redo in the native menus (the spell-check menu that Shift+right-click opens, and the macOS Edit menu) go to the renderer, which runs the focused editor's undo history. Chromium's own undo knows nothing of those histories. A plain text field, such as the find card's, keeps Chromium's undo.

`electron/spellcheck.ts` applies the enabled flag and saved language list to the native session at startup, after Settings Save, and after external settings changes. It uses Electron's existing custom dictionary rather than copying words into a second store. The language list defaults to system preferences, maps regional codes to the available dictionaries, and ignores unavailable saved codes without deleting them from settings. macOS retains system-controlled language selection.

Editable right-clicks reach Electron before Downpad shows its custom menu. The main process sends the clicked word and suggestions with a context identifier, converting native coordinates by the window zoom factor. The renderer adds spelling choices to its existing menu and restores editor focus before replacement. Replacement and dictionary actions must match the current native context, which is discarded on dismissal, another context menu, or navigation. Specialized image and tab menus still handle their own clicks. Shift+right-click requests the native menu.

Document prose inherits the spelling setting from its editor host. Milkdown attributes exclude inline code, and ProseMirror decorations exclude code-block node views. Embedded CodeMirror editors always disable spelling. The Markdown pane uses a CodeMirror compartment for its enabled flag and syntax-tree decorations to exclude visible inline, fenced, and indented code as edits and scrolling change the view.

The print workspace mounts a rendered copy of the document in the app window. Before pagination, the copy restores complete code blocks and their line numbers, including folded lines and offscreen blocks that Crepe has replaced with placeholders. Temporary editors used to restore placeholders are destroyed without changing the live document. Electron prints that document using the selected printer or writes a PDF. Printing waits for the workspace to finish rendering before starting the job. Downpad lays out the sheets itself and breaks pages between blocks. A block taller than a page continues on the next page. A paragraph or heading, and a line of the Markdown version, split between the lines they wrap onto, and inline formatting such as bold text or a link carries on across the break. A quote, a footnote, or a list item splits between the blocks it holds, and a table, list, or code block between its rows, items, or lines. What cannot be split, such as an image or a single table row taller than a page, is scaled down to fit the page instead of being cut off. A heading, or a run of headings such as a heading and its subheading, goes on the page of the first block after it that holds content, or of that block's first piece, so a page does not end with a heading whose text starts on the next page. Empty paragraphs, such as an empty line saved as `<br />` or one that holds only spaces, bold or not, and horizontal rules between them move with the heading. Elsewhere such blocks are packed like any other block. The Document version does this on the page and inside a split quote, footnote or list item. When the headings and that block do not fit an empty page together, for example before a piece of a split block that fills a page, the pages break as they would without the rule, since moving the headings would leave them alone on a page. The Markdown version prints source lines and keeps no line with the next.

The frontend can also run in a browser-backed development environment with platform operations represented by adapters. This allows most interface and editing behavior to be tested independently of the desktop shell.

## Updates

Downpad updates itself without electron-updater, which cannot install the MSI that Windows builds produce. The main process reads GitHub's latest-release API, which lists only stable releases, and downloads the release file named for its own package format, as the release workflow names it (`assetName` in `electron/updatePlan.ts`). It hashes the download while it streams to disk and keeps it only if the SHA-256 digest matches the digest that the API lists for that file. The trust in an update therefore rests on HTTPS to GitHub's API, since the packages are not code-signed.

`electron/updater.ts` keeps one folder per package format under `updates` in the user data folder, with the format's state file and at most one verified download, so an AppImage beside a DEB installation never touches the DEB's download. The next start installs the download before it opens a window (`electron/updateInstall.ts`). Installation copies the download once more, hashing the bytes it writes, and hands only that verified copy to the installer:

- An AppImage copy goes beside the running image and is renamed over it, so a crash leaves the old or the new image. Downpad then starts the new image.
- A DEB copy goes to a temporary folder that apt can read, and `pkexec apt-get install -y`, or `dpkg -i` without apt, installs it. Downpad then starts again.
- An MSI copy goes to a temporary folder, and a detached `cmd` helper waits for Downpad's process to end before it runs `msiexec /passive`. The helper reads its standard input, a pipe from Downpad, with `set /p`, which returns once the pipe closes as the process ends, so the copy that handed over the update has ended before Windows Installer checks for files in use. Downpad records the helper PID and process creation time before releasing that pipe. An extra start with no completed result checks whether that same process is still running and exits if so, retaining the pending state. Checking creation time prevents a reused PID from blocking later starts. Lookup failures retry once, then retain the handoff until a later launch can identify the helper or read its completed result. If the helper has exited, startup rereads the result to cover completion during the process check, then reports interruption only when no result exists. Legacy handoffs without a process identity get a ten-minute completion window. The helper then writes the installer's exit code to `install-result.txt` in the updates folder, removes the copy and starts Downpad, also after a failed or cancelled installation. Downpad forgets the download once the copy is verified and before the helper starts, so a failing installation cannot repeat on every start. It records the version it handed over, and the next start reports the installer's error if that version is still not running.

Check for updates in Settings restarts Downpad once the download that the check ends with is ready (`UpdatesBox`). The restart goes through `AppRuntime.restartToUpdateIfSaved`, which first checks `FileService.canCloseTabs`, so the close guard asks nothing. Settings skips the restart while its form reads differently from when it opened, the accent picker holds a draft colour, or the dictionary dialog is open. Quitting must not discard staged preferences or interrupt dictionary editing. Settings also skips the restart after its dialog closes, so a restart never interrupts work outside Settings.

A copy updates itself only if it can tell how it was installed: the AppImage runtime's variables for an AppImage in a writable folder, dpkg's file list of the `downpad` package for the DEB, and on Windows the `InstallDir` that the MSI writes to `HKCU\Software\Downpad` (`scripts/brand-msi.mjs`), read from `reg export`'s UTF-16 file, since `reg query` prints in the console's code page. Copies that do not match, such as unpacked builds, copies of the installed folder and installations for all users, only offer the release page. So do builds with the version `0.0.0`, which have no release tag.

`DOWNPAD_UPDATE_API_URL` replaces GitHub's API for tests and then also accepts plain HTTP from this computer.

## App icon and installer images

The app icon is a blue tile with a white block M above a yellow open chevron, the down arrow of the Markdown mark. `scripts/icons.mjs` draws the icon and every installer image as SVG, and `pnpm icons` renders them into `build/` with Playwright's Chromium, which `pnpm exec playwright install chromium` installs. The generated files are committed. `pnpm test:icons` checks that each file in the generator's list exists with the listed size, and that the generated text files are current.

- Below 64 px the M's straight edges and the chevron's top fall on whole pixels, so the icon stays sharp on a taskbar.
- The app draws the same M and chevron itself as the icon on the About page. `pnpm icons` writes their paths to `src/components/appGlyph.ts`. Recent rows use Lucide's `file` icon at 26 px.
- Windows uses `build/icon.ico`, whose frames from 16 px to 256 px cover display scales from 100% to 400%. Linux packages install the PNG files in `build/icons/` into the hicolor icon theme. The window icon is `build/icon.png`.
- The macOS icon in `build/icon.icns` follows Apple's grid, a rounded square 824/1024 of the canvas with a soft shadow, so it matches other apps in the Dock.
- The MSI shows `build/msi/dialog.bmp` on its welcome and finish pages and `build/msi/banner.bmp` across the top of the other pages. `scripts/brand-msi.mjs` adds both to the WiX project that electron-builder writes. The DMG window uses `build/background.png` and `build/background@2x.png`.
- `build/appx/` holds the images for an MSIX package for the Microsoft Store: the package logo, the taskbar and Start icon at every target size and theme, and the Windows 10 tiles. electron-builder's `appx` target reads them from there. That target is not enabled yet, so no MSIX package has been built from them or checked with the Windows App Certification Kit. `build/store/app-tile-icon.png` is the 300 × 300 px app tile icon for the Store listing in Partner Center.

## Design priorities

- Keep Markdown portable and directly editable.
- Make the formatted document view the default without hiding the source.
- Avoid content loss when switching views, tabs, or application sessions.
- Keep native capabilities behind focused backend services.
- Prefer a small, responsive desktop application over a broad workspace platform.
