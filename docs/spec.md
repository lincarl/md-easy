# Downpad product specification

Downpad is a desktop Markdown editor for Windows and Linux. It is designed for people who want to read and edit Markdown as a formatted document while retaining direct access to the source when needed.

## Core experience

- Edit Markdown in a clean WYSIWYG document view.
- Format selected text with a floating toolbar whose first buttons are H1, H2, H3, and H4. These set the heading level of the selected text blocks. The toolbar also offers bold, italic, strikethrough, inline code, and links, with no math button. Math remains available through Markdown and the block menu.
- Click the block handle's "+" on an empty paragraph or heading to open the block menu on that row without inserting a new row. On other blocks, "+" inserts a paragraph after the block and opens the menu there.
- Switch between Document, Markdown, and side-by-side Split views. A view chosen while a document opens or reloads takes effect once the document is shown, and choosing another view or tab before then does nothing. If the Document view cannot show a file, for example one with thousands of nested quotes, that tab opens in the Markdown view and the notice bar under the tabs says why. Try again shows the Document view once the text allows it, for example after a fix in the Markdown view. Other tabs keep the chosen view, and printing such a file prints its Markdown.
- Keep the rendered document and Markdown source synchronized, including edits made in the Markdown view while the Document view opens.
- Work with multiple documents in tabs.
- The main toolbar starts with Recent and ends with Settings at the far right. Narrow windows offer Document, Split, and Markdown in a compact view menu.
- Copy, immediately left of Print, opens the choices "Copy as markdown" and "Copy formatted text". Both copy the whole active document with its latest edits, in any editor view. Markdown preserves the source. Formatted text provides HTML formatting and readable plain text for pasting into other apps. Frontmatter, formulas, and diagrams retain their source as code, and linked images are not embedded. Copy is disabled on Recent.
- Open, create, save, and print Markdown files using familiar desktop controls and shortcuts. A printed paragraph, quote, footnote, list, table, or code block too long for one page continues on the next page, and so does a line of printed Markdown source. An image or other block that cannot be split is shrunk to fit the page. A heading that would end a printed page moves to the next page with the start of the content after it, as in a word processor, along with any empty lines or rule between them. It stays if the two do not fit on one page together, such as before a block taller than a page.
- Find and replace text within the active document from a find card that opens over the top right of the page. In the document view this includes the keys and values in the frontmatter table. YAML that the table shows read-only, such as a list, is found but not replaced. One undo takes back a Replace all in both the table and the document. Find scrolls each match it moves to into view, clear of the card. The whole card, with all of its controls, fits in the window at every window width.

## Markdown support

The editor supports common Markdown and GitHub Flavored Markdown features, including:

- Headings, paragraphs, emphasis, links, and block quotes.
- Ordered, unordered, and task lists. A click on a list item's bullet or number puts the caret at the start of its text, and a drag from there selects to the pointer. While the document has focus, Shift+click there extends the selection to the start of the text. A click on a task's box toggles the task. From outside the document, such as from the find card, the Markdown pane or a code block, it also puts the caret at the start of the task's text.
- Tables, horizontal rules, inline code, and fenced code blocks. A click in a table cell puts the caret where it lands, as in a paragraph, so a click right of a cell's text puts it at the end of that line. A drag across cells selects them, and so does a drag from a cell out of the table, so a text selection across a table starts outside it. A block dragged by its handle, or text dragged within the document view or from elsewhere, such as another app, and dropped on a table or beside it goes in above or below the whole table, at the table's edge nearer the pointer. The drop line marks that edge. The line follows the pointer, also while the page scrolls under a still pointer, and a drop goes in where the line shows. It hides where a drop would leave the dragged block where it is, and once the drag leaves the document. What is dropped never goes between the table's rows or cells, and a block or text dragged within the document view leaves the place it was dragged from, also when the page scrolls during the drag. With Ctrl held, or Option on macOS, the drop puts in a copy instead, and the drop line shows where the copy goes in, even right beside the dragged block. When that edge of a tall table is out of view, the page scrolls to show what was dropped. A click on a row or column handle, or on the button that adds a row or column, selects that row or column and opens its menu, and the next key goes there, also when focus was outside the document. A drag of a row or column handle that moves no row or column leaves the caret or selection where it was, so the next key goes there. The header row has no menu, so a click on its handle only selects it. After Delete in a row's menu, the row that moves into its place is selected with its menu open, so Delete again removes that row too. A menu closes once its row or column is no longer selected, so a click above a table after a Markdown edit of a cell in the split never selects or deletes a column. A faded table handle or menu shows again under the pointer before it takes a click. A fence keeps the options after its language, such as `title="server.js"`, and a `latex` fence stays a fence rather than becoming a math block. A block dragged by its handle, or text selected in the document view, and dropped on a fenced code block, a math block or a Mermaid diagram, including its toolbar and preview, goes in above or below it, at its edge nearer the pointer, where the drop line shows, also for a copy right beside the dragged block. A move leaves the place it was dragged from, and the code stays as it was. Text dragged in from elsewhere, such as another app, or within the code still goes into the code at the pointer.
- Syntax highlighting for code blocks, and VS Code's Markdown colors in the Markdown view. There a `$$` formula outside a list or quote keeps the body color, as fenced code does.
- Inline and block math rendered with KaTeX. Dollar signs follow Pandoc's rules, so prices such as `$5` and `$10` stay text, both in opened files and while typing. A typed closing `$` or `~` becomes math or strikethrough once the next character, Enter, moving the cursor out of the text it closes, leaving the editor, Save, or another edit such as a paste shows that Pandoc or GFM would read the same text that way. Autosave saves it as Save would but leaves it waiting on screen, so a digit typed next still keeps it text. A typed tilde right after a letter or digit opens no strikethrough, so `10~20` stays text, and a `$` or `~` in code stays code text. A formula right before a digit is saved as `$$x$$`, a `|` in a formula in a table cell as `\|`, and a paragraph that is only `$$...$$` is a math block.
- Mermaid diagrams rendered from fenced `mermaid` blocks using Pele. Diagrams follow the document theme and print in light colors. Pele uses its own layout and styling and targets Mermaid 12.1 syntax.
- YAML frontmatter, editable from the document view or as source. With Show frontmatter table enabled, a recognized leading frontmatter block has a Frontmatter disclosure above the document, collapsed by default. A document without a frontmatter block has no disclosure or Frontmatter tab. Empty, comments-only and unsupported blocks still have the disclosure. Opening it shows the editable table or read-only YAML in the document flow, without a separate scroll area or a height limit. Opening and closing it preserve the YAML, do not mark the document as changed and add no undo steps. Its open or closed state stays while that document pane lives, including switches between Document, Split and Markdown and between retained tabs. Find opens it when revealing a frontmatter match, and undo or redo opens it when returning the caret to a changed frontmatter cell. The global Show frontmatter table setting hides the whole disclosure when disabled and always preserves the YAML in the Markdown source. In the document view, edits in the frontmatter table and in the document share one undo history, so undo and redo go through them in the order they were made. A click on the table outside its keys, values and buttons leaves the caret where it was. The text of a read-only key or value can be selected as on a web page.

## Files and attachments

Markdown files can be opened through the file picker, recent-files view, drag and drop, command-line paths, or desktop file associations. A drop of several Markdown files opens each of them. The app preserves the document's line-ending style and warns before unsaved work is lost. Opening, copying or saving a file without edits keeps its exact text. Reloading a file that changed on disk shows its new text, also when the view is still changing, and typing in the Markdown view while it reloads is dropped rather than bringing the old text back. An edit in the document view rewrites only the blocks it changes, such as a paragraph, list or table. It keeps the file's text for the other blocks only where it has checked that the saved text reads back as the document. Otherwise, such as when two lists would join, it rewrites the whole body. A document counts as unsaved while its text differs from the file, so undoing every edit marks it saved again. While a save is still being written, and for a recovered snapshot until it is saved, the document stays unsaved.

Images can be pasted or dropped into a document. They may be embedded as base64 data or stored in an attachments folder beside the Markdown file. Other dropped files are copied to the attachments folder and inserted as links. A file dropped on the document view, alone or in the Split view, goes in at the block edge nearest the drop point, where the drop line shows, as a block dragged to that line would. Two cases differ. In a list, a link goes in as an item of its own where such a block would become a second block of an item and make the list loose. A list item cannot start with an image, so an image at the start of an item goes in before the item, which splits the list there, or before the list at its first item. A file dropped on a table, or on a code block, math block or Mermaid diagram, goes in above or below it, at its edge nearer the drop point, where the drop line shows. Above the text, including on the frontmatter table where no drop line shows, a file goes in at the start of the text, and below the text at its end. On the Markdown view, or the Split view's Markdown pane, a file goes in at the text position nearest the drop point. On an image's base64 data, it goes in after a Markdown image's closing parenthesis, and otherwise, as in a reference definition, HTML or code, as a paragraph of its own after the block that holds the data. A code block or HTML comment that is not closed yet would take in text after it, so there the file goes in before the block. The pane a file is dropped on then takes focus with the caret after the file, or after the last file of a drop of several, unless the user has moved on since the drop, for example with a click or a key, or is typing in that Markdown pane. While the Split view's Markdown pane has focus, a file dropped on the document pane still goes in at the drop point, and the Markdown pane makes the matching change to its source as the user's own edit. Focus and the caret stay in the Markdown pane, the rest of the source stays as written, and only a list or other block the file joins is written in the document view's form, with a blank line on each side. An empty list item in it stays empty, unless the document view needs the `<br />` it writes there, as before an image that goes into the item. A caret in a line of that block whose text stays keeps its place in that text, even when the line moves down for the file, its list item gets a new number or marker, or the document view writes the text another way, such as with an escape added, an entity decoded or a trailing space dropped. A caret at the start of such a line or before its marker stays there. A caret in an empty item stays in that item. If that change would not read back as the document shows it, as in a code block that is not closed yet, the Markdown pane takes the document view's form of the whole text instead. Dropped anywhere else, such as on the toolbar or the find card, it goes in at the caret of the pane being edited, after any selected text. The files of one drop keep the order they were dropped in, each after the one before, even when the caret stays where the user left it. Separate drops and pasted images keep their order in the same way. A file goes in only after the files dropped or pasted into its document before it, so a small file dropped while a large one is still read waits for it. A drop or paste that goes in at a caret, because it was dropped away from the text or its place is gone, goes in after the files that the drops and pastes before it put in at a caret while it was under way, as the files of one drop do. In the document view, a link dropped that way joins the line at a caret inside the line, and an image goes in after the line, so the line is not split. At the start or the end of a line, a file goes in before or after the line's block, as one dropped on that edge would, so a heading or a table is not split either. A file goes only into the document it was dropped on. A drop that also holds Markdown files puts its other files in first, in the same way. It opens the Markdown files once those are in, or as soon as the document they were dropped on is no longer in front, and the last Markdown file of the drop ends in front. A slow file dropped or pasted into that document before the drop holds back these Markdown files too, as it holds back the drop's other files. A Markdown file opened before the dropped file is in, by the same drop or another way, never replaces the document the file was dropped on, even if that is an empty untitled document. From the drop until the file is in, the document counts as unsaved, so closing it or the window asks first, even if a save of it finishes meanwhile. If another tab is in front by the time the file is read, the file waits until that document is shown again. An untitled document that needs a folder for the file asks where to save it then. It then goes in where it was dropped, also after a switch to another view, until the document is edited in the view shown. If that place is gone, for example after such an edit, it goes in at the caret of the view being edited. A file meant for the document view, dropped on it or while it was being edited, that goes in at the Markdown view's caret instead goes in as a paragraph of its own after the block that holds the caret, so it never joins the line, a heading or the frontmatter there, or splits a `$$` formula. In the Markdown view, a file that goes in is an undo step of its own, apart from typing right before or after it. A file stored in the attachments folder goes beside the document where it is saved as the file goes in, and its link leads from there. The file is stored only once the files dropped or pasted into its document before it are in. A Save As of the document, or a first save of an untitled one, that is under way then, with its dialog open or its file being written, finishes first. If the document is saved in another folder while the file is written, or an image's file is looked up, the file is written again in its new folder, and the copy in the old folder stays. An embedded image does not wait for a Save As. A file of a drop that cannot be read or stored, for example one deleted since the drop, is left out, and the drop's other files still go in. Find and replace cannot damage an embedded image. The document view does not search image sources, and the Markdown view skips the base64 data of every `data:` URI, including one written as text in a code sample.

An image keeps its alt text and title when the document is saved. An image on its own line can be resized in the document view, but plain Markdown has no place for the size, so the size is not saved. An image chosen in an image block's upload input, or with Replace image, goes into the Markdown view too if the user switches to it while the image is stored, and typing there afterwards is saved. A pasted or dropped image stored as a file goes in once Downpad has looked up its file, waiting at most a second for that, so it shows at once rather than as a missing image first. Shift+click on an image inside a line of text extends the selection to the side of the image clicked, and a Shift+drag from there extends it to the pointer, as on text.

When the document view cannot load an image, such as a local file that was moved or deleted, it shows the image's path in its place. An image on its own line becomes a placeholder that reads "Missing image. Click to locate it." above the path. An image inside a line of text becomes a small chip with the path, and its hover text reads the same words. A click on either opens a file dialog, and the image's path in the Markdown becomes the chosen file's path. A file chosen at the path the image already has, such as one that was put back, shows without a change to the Markdown, the undo history or the unsaved mark. Only a plain click locates the file. Ctrl or Cmd+click on a chip inside a link opens the link instead, Shift+click on a chip extends the selection to it, and other clicks with Ctrl, Cmd, Shift or Alt held open nothing. The placeholder and the chip never change the Markdown or the saved file. Print shows a missing image's alt text.

Local Markdown links can open their targets in another tab. External links open in the default browser. Ctrl or Cmd+click on an image inside a line of text opens the image's own link, and a double-click opens it when it points to a Markdown file. Both halves of the image count, so a link right after the image never opens instead, and an image without a link opens nothing. Text works the same way. Ctrl or Cmd+click anywhere on a link's text, including the right half of its last character, opens that link, and so does a double-click there when the link points to a Markdown file. The preview that shows while the pointer rests on a link's text is of that link too, and none shows on the URL after a link. Its Edit and Remove buttons act on the whole link, also one that holds an image and a caption or bold text. Shift+click on a link's text extends the selection to the click, and a Shift+drag that starts there extends it to the pointer and scrolls the document while the pointer is above or below it, as on other text. After a key that edits the text while the button is still down, such as Backspace, the drag goes on from where the key left the caret. Unlike on other text, the selection grows by characters also after a double-click selected a word. With Shift held, a double-click on a link's text only extends the selection, also on a link to a Markdown file. While focus is outside the document, such as in a code block, the Markdown pane or the find card, Shift+click on the document's text, including a link's text, the URL after it and the text of a table cell, puts the caret at the click, and Shift+click on an image inside a line of text puts it beside the image. Shift+click in the space beside or below the text, such as in a table cell right of or below its text, puts the caret where a plain click there puts it. This holds also when the document's caret was left in another table cell or cells were selected. The next key goes there, and a Shift+drag from there selects from the click, or selects the cells it crosses in a table, as a plain drag does. Shift+click from there on any other part of the document, such as a code block's toolbar, edge or preview, a list item's bullet, a rule, an image on its own line, a table's handle or a cell of the frontmatter table, does what a plain click there does, so the next key never replaces text in the editor that had focus. So does Shift+click anywhere else in the window, such as on the empty part of the tab strip. A click or Shift+click on the page around the document view or the Markdown view, such as beside the document's column, at any height, or in the margin of the column or a split pane beside the text, leaves focus and the caret where they were. A click below the end of the document, in the document view's bottom padding or on the page below it in the document's column or the split's document pane, puts the caret at the end of the document, as most editors do, and the next key goes there on every platform. After a paragraph or a heading, that is the end of its last line. After any other block, such as a list, a quote, a table, a code block, a math block, a Mermaid diagram, an image, a rule or a block whose code is hidden, it is the empty line the document view keeps after it, so the next key starts a new paragraph and never replaces or goes into the block. A drag from there selects from the end to the pointer, so a click that moves a pixel or two only puts the caret, and Shift+click there while the document has focus extends the selection to the end. From outside the document, such as from a code block, the Markdown pane or the find card, or while a block such as an image on its own line or table cells are selected, it is a plain click. A click below the end of the Markdown view or the split's Markdown pane, on its text, on its line numbers or in the room find adds below the last line, puts the cursor at the end of the Markdown, with focus there. A drag from there below the text, and a Shift+click there while the Markdown has focus, work as on the Markdown's text. A click in the document view's side padding beside a block, left or right of its text, puts the caret on the line at the click's height, at the line's start on the left and at its end on the right, as beside a paragraph. Beside a list item that line is the item's text, and beside a table it is the row's first cell on the left and its last cell on the right. Beside a code block, a math block or a Mermaid diagram, the code takes focus with the cursor at the start or end of its line at that height, or of its nearest line beside the toolbar or the preview. Beside an image on its own line or a rule, the click selects it, as a click on it does. The next key goes there, also when text was selected before, and a drag from there selects to the pointer, or, while the pointer is beside the text, to the start or end of the line at its height, so a click that moves a pixel or two only puts the caret. A drag from beside a code block selects in its code, as a drag in the code does, until the button is released, Esc is pressed or the window loses focus. Shift+click in the side padding while the document has focus extends the selection to the line's start or end. Beside a code block, an image or a rule, from outside the document, or while a block or table cells are selected, it is a plain click. After the document view changes width, such as on a switch from the Document view to the Split view, the block handle hides until the pointer moves over the document again, and then shows beside the block under the pointer at once, without sliding there. So a click right after the switch reaches what is under the pointer, such as a list item's bullet or a task's box. A click on the text next to a link opens only that text's own link, if it has one, and a click on the empty space beside a line opens nothing. Ctrl or Cmd+click puts the caret where it lands, as a plain click does, also inside selected text, a block the block handle selected or a selection of the whole document. It never selects the whole paragraph, heading or list item, so the next key cannot replace a whole block or selection. One that opens no link selects an image under the pointer instead, as a plain click does, but never opens a missing image's file dialog. One that opens the link of an image puts the caret beside the image. In a code block that already has focus, Ctrl or Cmd+click adds another cursor. In a code block that does not have focus, and in the split's Markdown pane while the document pane has focus, Shift+click puts the cursor at the click. A click on a line number in a code block or the Markdown view puts the cursor at the start of that line, and Shift+click there while the editor has focus extends the selection to it. A click or Shift+click on a fold arrow folds or unfolds its section, and one there or in the space beside it leaves focus and the cursor where they were. A click from a code block on another part of the document, such as an image on its own line, a task's box or the block handle's add button, moves focus to the document, where the next key goes. A code block's language button opens its picker, whose search field takes the next key, and its Copy button takes focus as a button does. The document view can show each link's URL after its text. Ctrl or Cmd+click on that URL opens the link before it, even when another link follows right after it. A click on the URL, with or without Ctrl or Cmd, puts the caret at the end of the link before it, and Shift+click extends the selection to there.

In the document view, text typed, pasted or put in by an input method at either end of a link goes outside the link, including after Backspace or undo. This holds at the end of a paragraph, list item, heading, quote or table cell, before a line break, and at the start of a line that begins with a link. Text typed where a link's whole text was deleted is plain too, and plain text dropped on a link does not take the link. Text typed right after a dropped file stays out of its link, also when a link to the same file follows, such as one to a missing attachment that the file fills. This holds after Backspace, Delete or undo there too, until the caret is moved. Typing inside a link's text stays in the link. Typing or pasting over selected text of a link replaces that text and keeps the link, so selecting a link's last character and typing extends the link. Where text follows a link, Left at the link's end puts the caret on the link's side without moving it. Right does the same at the start of a link that follows other text. The caret's tail shows that side. Typing there goes on in the link, also after Backspace or Delete takes some of the link's text, until the caret is moved, such as with an arrow key, a click or Enter. The opposite arrow key puts the caret back on the side of the text next to the link, and so does deleting that text next to the caret or the link's whole text. With the URL shown after links, a caret at the end of a link is drawn after the URL when the next character goes there, and before the URL on the link's side.

## Paste behavior

Downpad adapts pasted content to the document:

- Images are inserted and stored according to the image settings. Images are pasted in the document view, alone or in the Split view. The Markdown view takes only the text of a paste, so an image alone on the clipboard puts nothing in there. A paste that also holds text or HTML, such as an image copied from a web page, puts in that content as described below instead of the image. In the document view, a pasted image goes in where the caret was when it was pasted, as a file dropped away from the text goes in at the caret. It goes in after any selected text or image, and from a caret or a selected image inside a line it goes in after the line, so the line is not split. From a table cell it goes in above or below the table, as a file dropped on the table does, on the side nearer the cell. Images pasted one after another at the same caret keep the order they were pasted in, even while the first is still being stored, because an image goes in only after the images pasted and files dropped into its document before it. The caret then goes after the image, at the start of the next text, unless the user has moved on meanwhile, for example with a click or a key. An embedded image goes in at once. An image stored in the attachments folder goes beside the document where it is saved as the image goes in, as a dropped file does. It is stored once the images and files pasted or dropped into its document before it are in, and a Save As of the document that is under way then, for example one still being written to a slow drive, finishes first. If the document is saved in another folder while the image is written or its file is looked up, the image is written again in its new folder, and the copy in the old folder stays. Until the image is in, the document counts as unsaved, so closing it or the window asks first. Meanwhile the user can go on editing, as with a dropped file. If another tab is in front by the time the image is stored, it waits until its document is shown again. A switch to the Markdown view keeps the place it was pasted, and the image goes into the Markdown source there. The place is gone once the document is edited in the Markdown view, after a reload from disk, and when the document view was built again, for example after its editor was dropped from memory behind other tabs. Then the image goes in at the caret of the view being edited, in the Markdown view as a paragraph of its own after the block that holds the caret. An image pasted while an earlier one is still on its way in, that also goes in at the caret this way, goes in after the earlier one. An image pasted into a document that is closed first goes nowhere, and no other document is saved for it. If the user cancels the save that an untitled document needs for an image stored in the attachments folder, nothing goes in.
- Markdown-looking plain text is inserted into the source, before accompanying HTML is considered.
- Other rich HTML from browsers and compatible applications is converted to Markdown.
- Pasting a URL over selected text creates a link.

Markdown text pasted into the document view is inserted into the Markdown source before rendering. Leading frontmatter appears as metadata rather than body text. Pasted source keeps its formatting, with line endings normalized internally. Leading and trailing line breaks stay alongside existing source separators. A partial paste may normalize the surrounding edited block, as other document edits do, while untouched blocks keep their source. If pasted delimiters conflict with existing marks, the edited block is written with compatible delimiters so surrounding formatting stays intact. The caret moves after the whole paste, including when its text repeats the selection. Pasted Markdown takes priority over accompanying syntax-highlighted HTML. Existing frontmatter stays when only the body is selected. One undo reverses the whole paste, including new frontmatter. Code keeps pasted markup literal. Pasting into selected table cells fills those cells without splitting the table.

## Keyboard

In the document view, Tab and Shift+Tab indent and outdent list items, move between table cells, and indent and outdent code in code blocks. In a list or table they stay in the document even where there is nothing to indent or no next cell. Elsewhere they move focus to the next or previous control outside the document, as in the Markdown view, and never type spaces. They also stay in the document while the block menu that "/" opens is showing. Esc closes that menu, and so does moving focus elsewhere in the window, such as with a click on the toolbar. The toolbar that shows over selected text in the document view hides once focus moves elsewhere in the window, such as to the split's Markdown pane, and shows again when text is selected in the document. Esc, then Tab or Shift+Tab within two seconds, leaves the document from anywhere in it. In a code block, Esc then Tab first moves to the block's language and Copy buttons, and Tab from the last of them leaves the document.

In the document view, End moves the caret to the end of a line that starts with an image, a formula or another inline item such as a footnote reference, in a paragraph, a list item, a heading or a table cell and after a line break, and Shift+End selects from the caret to there. After a line break the selection starts after the line break, and it keeps starting there when Shift+End is pressed again or Shift with an arrow key, Home, Page Up or Page Down changes it. Typing over a selection replaces what it covers, so it keeps the line break when the selection starts right after the break and replaces the break when the selection ends there. An emoji and text from the emoji panel or an input method replace it the same way. A key typed while a block is selected, such as an image on its own line or a code block selected with its handle, replaces the block, also when the window was left for another app and activated again or a dialog such as Save As closed in between. After a press or a drag on a block's handle, from anywhere in the window, such as from a code block, the find card or the Markdown pane, the next key replaces the block the handle selected, or the block the drag moved, also a code block. That holds for a drag cancelled with Esc, dropped back where the block was or dropped outside the document. Shift+drag on the handle selects the block without moving it. Text from an input method, the emoji panel or dictation replaces a selected block or selected table cells as a key does, so an image between two paragraphs gives way to the text and the paragraphs stay apart. That holds for an input method's composition too, as Japanese, Chinese and Korean input methods type, and for one over a selected image or formula in a line, whose text keeps the formatting a key's text keeps, such as a link or bold, and comes in once between two images. One undo brings the block, the cells or the image back. A composition that commits nothing, such as one cancelled with Esc, leaves them as they were, selected, so the next key replaces them, and leaves undo and redo and the focus as they were. Text that an input method commits right after it, as IBus does, is an undo step of its own. Over a block between two blocks that take no caret, such as an image between two code blocks, Chromium often passes no such text on, and then none goes in. Over selected text or a formula at the end of a link's text, a composition whose steps add to its text, as Japanese input methods type, can get the first step's text twice, and one cancelled can keep that text, because Chromium types the later steps after the link.

## Recent files and recovery

Unsaved documents show a red document icon in their tab, while the window title shows only the file name and app name. Closing a tab, all tabs, or the window offers Save, Cancel, and Discard when there is unsaved work. Save writes each affected document and asks for a path for an untitled document. Cancelling a save, a failed write, or work still waiting to be saved keeps the documents open.

The Recent button sits in the menu row, immediately left of Open, and uses the same toolbar styling with a Lucide list-clock icon. The Recent view lists previously opened documents, with starred favorites pinned at the top. Its search field finds documents by file name, by content, or both.

Settings > General > Recent files includes Default search with Names, Contents, and All (names, then contents). Names is the default. The selected default applies whenever Recent opens. Keep removed files in list is off by default, hiding missing files from favorites, recent rows, and search results without deleting their history. Enabling it shows missing entries with their existing locate and remove actions. Returning files appear on the next refresh.

The app periodically stores a separate recovery snapshot for each tab with unsaved work, including background tabs, and offers to restore them after an interrupted session. Saving or discarding one tab clears only its snapshot. An accepted shutdown waits for pending snapshot writes before clearing the session's snapshots. If opening an original file fails, the recovery dialog shows an error and keeps the recovered work available to open or retry. Optional autosave can save changes to files that already have a path.

Downpad reopens the documents that were open when it last closed, in the same tab order and with the same document active, also after a crash or a restart that installs an update. Untitled documents are left out. Files that cannot be read, such as files on an unmounted drive, keep their place in the saved session for later starts without opening an editor. Closing every visible tab clears the saved session, including those unavailable files. Recovered work opens first, so its file does not open a second time. A file that Downpad starts with, such as one opened from the file manager, opens beside the reopened documents as the active one. With nothing to reopen or open, Downpad starts on the Recent view.

## Appearance and preferences

Settings > Spelling enables spell checking for prose in Document, Markdown, and Split views. Inline code and code blocks are excluded, including newly typed code. Normal right-click on a misspelling offers corrections and Add to dictionary before the existing editing commands. Corrections preserve surrounding formatting and support Undo and Redo. Shift+right-click keeps the native editing menu.

Spelling marks follow the native checker's timing. Text loaded into an automatically focused editor may wait for typing or for the user to focus the editor again before it is checked.

On Windows and Linux, choose several spelling languages or follow the system languages. The choice is saved in `spellCheckLanguages`, with an empty list meaning system languages. Unsupported saved languages remain in the preferences but are not used on that device. If none are supported, the checker uses system languages. macOS manages its languages through System Settings. Language dictionaries download when first needed, and spelling is checked locally without sending document text to a spelling service.

Manage dictionary lists words added to Downpad's native dictionary and allows adding or removing them. Changes take effect immediately and survive restart, independently of Settings Save or Cancel. Existing custom words remain available. On Windows and macOS, adding or removing a word also updates the operating system's custom dictionary. Browser development builds retain browser spelling but require the installed app for these language and dictionary controls.

The interface shares the look of Mervin PDF. Users can choose light, dark, or system themes; adjust the accent color, document width, font, and text size; select the default editor view; and configure image storage, Markdown serialization, spell checking, recovery, and autosave behavior.

The document's side margins narrow in a narrow window or Split pane, and with a fixed document width below 688px in any window, so its text keeps a readable width.

Settings are stored locally in `settings.toml` and can be changed from the app or by editing the settings file.

If the file contains invalid TOML, the app uses defaults for the session and preserves the original file. Settings changes apply in memory, but saving them requires repairing the file's syntax first.

## Updates

Copies installed from a release's MSI installer, AppImage or DEB package update themselves. With Update automatically on, which is the default, Downpad checks GitHub for the latest stable release when it starts at least 30 days after its last successful check, or when it has never checked. A failed check stays due and runs again on the next start. A newer release downloads in the background in the same package format, and Downpad keeps it only if it matches the SHA-256 digest that GitHub lists for it. The next start installs it before any window opens and starts the new version. The MSI installer starts once Downpad has closed and shows its progress without asking anything. The AppImage file is replaced, and the DEB package installs after the system asks for a password. If that start cannot install the download, or the password prompt is dismissed, Downpad deletes the download and waits for the next check, and an installation error is shown once the window opens. On Windows, an extra start while the update helper is running closes without showing a failure or opening a window that could lock application files. Downpad starts again after the installer, also after a failed installation, and then shows the installer's error. MSI upgrades include removal of the previous version in the installation transaction, so a failed upgrade restores it. A cancelled installation shows nothing. An interrupted helper reports that installation did not finish. The helper is identified by both its process ID and creation time, so a reused process ID cannot block later starts. A failed lookup keeps the installation pending instead of reporting failure or opening files that the installer may still be replacing.

Settings > Updates shows the version, the automatic update switch and Check for updates. Check for updates reports that Downpad is up to date or that the check failed, or shows the download's progress. When the download is ready and Settings is still open, Downpad restarts at once to install it, unless a document has unsaved changes or Settings has changes that Save has not written. It then offers Restart now, as it also does for a download that is ready when Settings opens, until Check for updates finds it again. Restart now asks about unsaved documents first, then starts Downpad again, which installs the update. Both restarts reopen the open documents. A download from Check for updates also installs on the next start with automatic updates off. Switching automatic updates off deletes a download that only they would install.

Installed copies update only to stable releases. A release candidate updates to the release of its own version or a newer one. Each package format keeps its own check date and download, so an AppImage beside the DEB installation never installs or deletes the DEB's update. Copies that cannot update themselves show no switch, and Check for updates offers the release's download page instead. These include development builds, builds from source, an AppImage in a folder Downpad cannot write, copies of the installed folder, and MSI installations for all users of a computer.

## Platform and scope

Downpad is a local, single-user Electron application for Windows and Linux. Documents remain ordinary Markdown files on disk. The app does not provide cloud sync, real-time collaboration, mobile clients, or a plugin system.
